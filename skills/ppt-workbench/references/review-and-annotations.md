# 预览、批注与视觉复查

## 前台与编辑源

用户在 Codex 原生预览中查看导出的 PPTX、选元素并提交批注。对由本工作台生成、且没有外部手改的稿件，HTML deck 继续作为编辑源；批注不意味着必须转为直接修改 PPTX。底层采用逐页源文件、稳定元素 ID、修改前快照、局部替换、Chromium 实测和原生 PPTX 导出。

用户若直接在 PowerPoint/WPS 或预览编辑器中更改了文档内容，以最新 PPTX 为事实源。当前没有无损反向同步，不以旧 HTML 导出覆盖手改结果。强制保留母版或复杂原生对象时同样选择原文件编辑路线。

## 处理原生预览批注

1. 核对批注的 artifact 路径和对应导出版本，读取实际提供的页码、标题、形状 ID/名称、选区和引用文字。不得假设未提供的字段存在。
   同时读出作用范围：元素、整页、一组页或全稿。选中一句话可以仅用于定位；用户明确要求整页重排时，不把选区当成只能修改该句的限制。scope 不明确且会影响未授权内容时再澄清。
2. 用对应版本 PPTX 的形状和文本定位，再与源页面及 deck_elements 的稳定 ID 核对。viewer slide ID、PPTX shape ID 和 data-ppt-id 是不同标识；shape ID 只在对应幻灯片和版本内使用。不能只凭形状序号将旧批注应用到新版。
3. 唯一匹配后读取当前元素哈希，通过 deck_edit_element 修改；复杂重排先保存快照再定点改源文件。匹配有歧义时只澄清目标，不猜测覆盖其他元素。
4. 批量修改后检查、修复、导出新的版本，记录对应源版本和本轮涉及页面。保持用户未要求修改的内容。

原生 PPTX 项目改用 pptx_inspect 读取当前页/对象，再 pptx_prepare 记录 scope 与可用 annotation 字段，通过原生修改和 review/commit 交付。详见 [原生精修](native-pptx-workflow.md)。例如批注：“【范围：整页】标题只用于定位，左侧机制、右侧示意图，保留已确认文案。”不要求前端提供新的整页按钮。

目前已有稳定源 ID 和快照工具，但没有通用的原生批注导入器，也没有自动维护完整的 PPTX shape → 源元素映射。上述映射需要实际检查完成，不能声称已全自动接入。

## 何时让模型看图

| 修改或判断 | 默认做法 |
| --- | --- |
| 文案替换、强调色、局部格式 | 检查目标元素与程序诊断；不默认读截图 |
| 初版整体排版、参考版式匹配、章节节奏 | 先看多页联系表，评估整体一致性与疏密 |
| 图片选择、裁切、美术升级、疑难溢出 | 看相关原图或清晰单页；整体风格变化补看联系表 |
| 完成一批局部改稿 | 视觉复查限于变化页及受影响页面，不重复读取未变全稿 |
| 最终交付 | 未验收的页面用联系表整体检查，细节风险页单独检查；已验收且未变部分复用记录 |

deck_preview 当前每张联系表最多 9 页、3 列，并保留单页 PNG。数量是现有实现，不是所有项目的固定视觉规范。联系表适合看版式节奏，不足以证明小字可读、文字准确或裁切细节正确。需要视觉判断时不能以节省图片为由跳过关键检查。

优先读取需要的联系表，再只放大有问题的页面；不要把联系表和所有单页默认一起读入。素材查阅结论写入 deck_media 或 notes/style.md，变化页与验收范围记录在项目记录中。只记录实际观察，不把图片路径生成成功写成视觉验收通过。

## 版本展示与刷新

默认交付 deck_export 生成的独立版本文件，保留 Codex 的原生批注入口；每轮提供最新文件。固定路径只能作为便捷副本，不能承诺覆盖后前台自动刷新。如果客户端确实显示刷新入口，可使用它；工具返回 queued 或 opened 不等于画面已更新。

不为刷新接入未经公开支持的客户端内部函数，不把新文件名伪装成实时同步。前台刷新方式不改变底层 deck 的编辑方式。当前也没有与 Artifact Session 共享画布双向同步。

本流程减少不必要的模型图片输入；它不能清除 Codex 历史图片、控制完整请求的图片总量或保证永不超限。
